Verified irregularities & assumptions (each with its official source)

Build-environment limitations (transparency)

  • Sandbox egress. The build environment only permits github.com / npm / pypi traffic, so Kalshi endpoints were verified through server-side page fetches (official API responses, quoted verbatim in the snapshot), not through a live browser. Browser CORS behavior is therefore unverified at build time; the site degrades gracefully to the verified snapshot and prints a manual curl CORS check in the banner.
  • WebSocket. Kalshi's WS requires authentication headers at handshake; a static page cannot set them without user credentials. REST polling is used instead (documented as having separate unauthenticated limits). Source: official WS quick start ↗.
  • Demo account connection. Real demo-account portfolio/order endpoints require demo API keys. None exist in this build, so account tracking is implemented as the simulated engine and the limitation is disclosed rather than faked. Source: official demo docs ↗.
  • News attribution. Alerts link a news search for the event title, labeled unverified. No claim about causation is made anywhere in the app.

Deliberate design choices (not irregularities, but visible)

  • Est. dollar columns are labeled estimates everywhere (volume × last price; OI × mid) because the API publishes contracts, not dollars.
  • Single-topic assignment — an event appears in exactly one topic tab (first-match-wins) to keep topics separate per the project brief; "All" views aggregate the five.
  • Model & bot parameters (thresholds, sizing, exits) are constants documented on the Strategies page rather than hidden magic.
  • Local persistence only — alerts, picks, resolutions, and paper trades live in your browser's localStorage; nothing is transmitted anywhere except read-only calls to the official API.

Manual verification commands (for review after go-live)

  • Golf whitelist: curl -sS "https://external-api.demo.kalshi.co/trade-api/v2/series?tags=Golf"
