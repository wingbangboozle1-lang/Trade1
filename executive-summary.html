Executive summary

What this dashboard is, what it does, what it deliberately does not do — and how each claim was verified

In one paragraph

This site is a static, read-only dashboard over the official Kalshi demo Trade API (https://external-api.demo.kalshi.co/trade-api/v2, the recommended demo host in the official demo docs). It watches live markets in exactly five topics — gas prices, elections, culture, crypto, golf — ranks them by an estimated traded-dollar figure, posts a chat alert for every price move of $0.10 or more in either direction into two scrolling feeds (all moves, and moves that pass a documented ROI screen), charts the YES price against time with seconds-to-hours windows plus order-book depth, and runs four automated paper strategies on live quotes so that strategies can be compared by strategy and by topic, with every position carried to its official YES/NO resolution.

The demo environment is play money; Kalshi's own documentation warns that demo prices and behaviour may not reflect production markets. Nothing here is financial advice, and no order is ever transmitted.

What is deliberately not built, and why

Not builtReason (with the official text that decides it)
WebSocket streaming The official docs state authentication is required to establish the WebSocket connection and the three KALSHI-ACCESS-* headers must be sent during the handshake. A browser cannot attach custom headers to a WebSocket, so a static page cannot connect. The site polls REST instead and states the resulting lag. Quick Start: WebSockets
Real demo-account balance / positions Account endpoints require signed requests with a private API key. The brief says there must be no manual input from the owner, and a public site must never handle credentials — so portfolio tracking is a local paper portfolio, clearly labelled. Quick Start: Authenticated Requests
Order execution on the exchange Same reason as above, plus safety: an unauthenticated public site that could place real orders would be a hazard. "Simulated trades" are recorded fills against official quotes, never transmitted. Create Order (V2)
Sub-second alert latency REST responses are cached: "prices, sizes and status can lag the exchange by several seconds". Sub-second swings are therefore not observable; the site says so instead of implying real-time precision. Get Markets (caching note)
Exchange-published dollar volume No such field exists in the market schema, so every dollar figure on the site is computed from contracts × price and labelled an estimate. Get Markets schema

Verification method

  1. Documentation first. Every endpoint, field name, unit and limit was read on docs.kalshi.com; the exact pages are listed on Sources.
  2. Live responses second. Field shapes were confirmed against live demo responses (for example orderbook_fp.yes_dollars as [price_dollars, count_fp] strings, and volume_fp as a contract count, not dollars).
  3. Automated checks third. CI runs the real dashboard engine in a headless DOM against captured response shapes (tests/engine.test.mjs), the offline library tests (scripts/test_lib.mjs), a syntax/link/nav check (tools/build.mjs), and a check that every snapshot row carries an official source URL (scripts/check_site.mjs).
  4. Blank beats wrong. Anything the API did not return is left blank and listed on Flagged for Review, with the source that was checked.

Suggestions to make the site more live and interactive

These are recommendations, clearly marked as not implemented — the current build is limited to what a static page can verify.

  1. Server-side watcher with a signed demo key. A tiny scheduled job (GitHub Actions already runs the data collector) could keep state between polls and push true WebSocket ticker/trade events into the committed snapshot, cutting alert latency from ~12 s to sub-second. It needs a demo API key stored as a repository secret — a decision for the owner, not taken here.
  2. Alert sound and browser notifications. A local, opt-in beep/OS notification when a ≥ $0.10 move posts, so the dashboard can be left on a second screen.
  3. Anchor the news link to a timestamp. The Google News search already jumps to a query; adding when:1h to the query string would bias it to recent stories. It remains a lead, never a cause.
  4. Cross-market confirmation. When one market in a mutually exclusive event jumps, show the sibling markets' moves side by side — a cheap way to distinguish a real repricing from a stale quote.
  5. Depth-weighted fill simulation. Walk the official order-book ladder to estimate slippage for larger paper sizes instead of assuming the top level fills everything.
  6. Persist alerts across devices. Alerts and paper trades live in localStorage; exporting them to the repo (like the snapshots) would make a shared, multi-observer history possible without any credentials.

429 storm in the snapshot collector. data/log.md for the 2026-11-21T06:58Z run records 220 × 429 against 45 × 200, leaving data/topics/gas-prices.json with 0 open events and the snapshot partial. The collector treated a failed read as an empty result, and neither Python fetcher retried a 429. The official Rate Limits and Tiers page says to back off exponentially on 429 and sends no Retry-After. Fixed across two merged sessions: session c96a21b7 (PR #80) made the collector's reads fail-closed — 5 attempts, Retry-After else 2ⁿ s capped at 60 s, every failure recorded, and a verified artifact is never overwritten by a degraded run.
