# Flagged for Review — Irregularities & Unverified Items (docs/FLAGGED.md)

Rule (from the project brief): **if a value can't be confirmed from an official source, leave it
blank and flag it as unverified. Never infer or fill in values.** Items below are also published on
the site's "Flagged for Review" page. None of these block the merge.

| # | Item | Status | Detail & what I did instead |
|---|---|---|---|
| F1 | **CORS behavior of the demo API is not confirmed by an official statement** | Unverified (behavioral) | Official docs publish browser-JS `fetch()` examples against the API ([Quick Start: Market Data](https://docs.kalshi.com/getting_started/quick_start_market_data.md)), which implies browser-origin requests are expected to work, but no doc states `Access-Control-Allow-Origin` explicitly. The sandbox cannot reach `kalshi.co` to test headers. **Mitigation:** the site detects failed fetches and shows a clear banner linking the exact API URL so it can be checked manually; it never fakes live data. |
| F2 | **Demo API credentials do not exist in this session** | Blocked-by-design | Authenticated endpoints (orders, portfolio balance/positions, WebSocket) require a demo API key signed per [API Keys](https://docs.kalshi.com/getting_started/api_keys.md). Creating the demo account is an interactive, human step (per [help article](https://help.kalshi.com/en/articles/13823775-creating-and-using-a-demo-account)) and cannot be done autonomously. **Mitigation:** the dashboard runs a fully automated **paper engine** on live demo market data (documented fee formula, $10,000 simulated bankroll mirroring demo mock funds). If/when demo API keys are pasted into the browser (stored locally only), the built-in signed-request connector can place real demo orders — the code path exists and is dormant. |
| F3 | **"Liquidity" field missing from current market responses** | Irregularity | The market object returned by the demo API (spec v3.37.0, verified live 2026-11-20) has bid/ask prices+sizes but **no aggregate `liquidity` field**. **Mitigation:** the dashboard computes liquidity from the orderbook (contracts available within $0.10 of the best bid per side) and labels it "computed from orderbook", with a link to the raw orderbook API call. |
| F4 | **Status vocabulary differs between filter docs and live field values** | Irregularity | `GET /markets` *filter* docs allow `unopened\|open\|closed\|settled` ([Get Markets](https://docs.kalshi.com/api-reference/market/get-markets.md)), but the live `status` field on market objects shows `active` and `finalized` (verified 2026-11-20). **Mitigation:** the app treats `active`≈open and `finalized`≈settled and tolerates both vocabularies. |
| F5 | **News links for price jumps are search queries, not verified causes** | Partially verifiable | The requirement asks for "website links that may have caused a sharp jump ≥ $0.10." Without a news API key, cause attribution cannot be verified. **Mitigation:** every jump row links (a) the official market page on kalshi.com, (b) the event's **official settlement sources** (from the API, e.g. EIA for gas, CF Benchmarks for crypto), and (c) a Google News query pre-filled with the market title — clearly labeled as a *search*, not a verified cause. |
| F6 | **Demo site has no public market webpage for direct deep links** | Irregularity | Demo markets live behind `demo.kalshi.co` (login required to trade); public `kalshi.com/markets/...` pages document the *production* contracts of the same series. **Mitigation:** row source links point to (1) the exact demo REST URL that produced the value (official machine-readable source) and (2) the official kalshi.com series page for the contract rules. |
| F7 | **Sub-cent/edge fields not exercised live** | Unverified at runtime | `settlement_bounds_type`, `collateral_return_type` values beyond defaults were not observed in live probes (no settled range market with partial payouts was sampled). These fields are displayed only when present, never inferred. |
| F8 | **"Highest dollar amount" ranking metric is a defined approximation** | Methodology (documented) | No official "dollar amount per event" metric exists. The dashboard ranks events by **Open Interest × mid-quote (YES bid/ask midpoint, USD)** and also shows **24h $ volume = volume_24h × last trade price**; both formulas are shown on the site next to the ranking. Raw contract counts are displayed alongside so nothing is hidden. |
| F9 | **KXPRES28 probe failed twice (fetch tool error, not API-verified)** | Unverified | A direct probe of `GET /series/KXPRES28` errored at the fetch-tool level twice; the 2028 presidential series is therefore *not* claimed as verified for demo. Elections coverage relies on the verified category `Elections` + live event discovery instead. |
| F10 | **Client polling can lag the exchange by several seconds** | Documented limitation | Official docs state market-data responses are **cached for a short time** and can lag the exchange by several seconds ([Get Markets](https://docs.kalshi.com/api-reference/market/get-markets.md), [Candlesticks](https://docs.kalshi.com/api-reference/market/get-market-candlesticks.md)). The site displays a "last updated" timestamp per panel and labels all prices with their fetch time. |
