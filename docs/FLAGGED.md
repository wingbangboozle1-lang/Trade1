# Flagged for Review — Irregularities & Unverified Items (docs/FLAGGED.md)

Rule (from the project brief): **if a value can't be confirmed from an official source, leave it
blank and flag it as unverified. Never infer or fill in values.** Items below are also published on
the site's "Flagged for Review" page. None of these block the merge.

| # | Item | Status | Detail & what I did instead |
|---|---|---|---|
| F1 | **CORS behavior of the demo API is not confirmed by an official statement** | **Closed with live evidence 2026-11-21 (`9b6ffae0`); no official statement exists** | Official docs publish browser-JS `fetch()` examples against the API ([Quick Start: Market Data](https://docs.kalshi.com/getting_started/quick_start_market_data.md)), which implies browser-origin requests are expected to work, but no doc states `Access-Control-Allow-Origin` explicitly. **Now measured on the live official demo host from a CI runner** (`data/cors.json`, probed 2026-11-21T07:19:44Z): `GET /exchange/status` with `Origin: https://wingbangboozle1-lang.github.io` returns `access-control-allow-origin` echoing that origin plus `access-control-allow-credentials: true` and `vary: Origin`, and `OPTIONS /markets` returns `204` with the same header — so the Pages site can and does poll the public endpoints directly. It also exposes `X-Ratelimit-Remaining/-Reset` to page JS. **Mitigation kept** (still correct): the site detects failed fetches and shows a banner linking the exact API URL so it can be checked manually; it never fakes live data. |
| F2 | **Demo API credentials do not exist in this session** | Blocked-by-design | Authenticated endpoints (orders, portfolio balance/positions, WebSocket) require a demo API key signed per [API Keys](https://docs.kalshi.com/getting_started/api_keys.md). Creating the demo account is an interactive, human step (per [help article](https://help.kalshi.com/en/articles/13823775-creating-and-using-a-demo-account)) and cannot be done autonomously. **Mitigation:** the dashboard runs a fully automated **paper engine** on live demo market data (documented fee formula, $10,000 simulated bankroll mirroring demo mock funds). If/when demo API keys are pasted into the browser (stored locally only), the built-in signed-request connector can place real demo orders — the code path exists and is dormant. |
| F3 | **"Liquidity" field missing from current market responses** | Irregularity | The market object returned by the demo API (spec v3.37.0, verified live 2026-11-20) has bid/ask prices+sizes but **no aggregate `liquidity` field**. **Mitigation:** the dashboard computes liquidity from the orderbook (contracts available within $0.10 of the best bid per side) and labels it "computed from orderbook", with a link to the raw orderbook API call. |
| F4 | **Status vocabulary differs between filter docs and live field values** | **Resolved 2026-11-21 (session `9b6ffae0`): not an anomaly** | `GET /markets` *filter* docs allow `unopened\|open\|closed\|settled` ([Get Markets](https://docs.kalshi.com/api-reference/market/get-markets.md)), while the live `status` field on market objects shows `active` and `finalized`. The official **response** schema documents exactly that: `status` ∈ `initialized \| inactive \| active \| closed \| determined \| disputed \| amended \| finalized` ([Get Events — Market schema](https://docs.kalshi.com/api-reference/events/get-events.md)). The filter enum and the status enum are two different documented enums, so `active`/`finalized` are conformant values, not a demo-only vocabulary. **Mitigation kept** (harmless): the app treats `active`≈open and `finalized`≈settled and tolerates both vocabularies. |
| F5 | **News links for price jumps are search queries, not verified causes** | Partially verifiable | The requirement asks for "website links that may have caused a sharp jump ≥ $0.10." Without a news API key, cause attribution cannot be verified. **Mitigation:** every jump row links (a) the official market page on kalshi.com, (b) the event's **official settlement sources** (from the API, e.g. EIA for gas, CF Benchmarks for crypto), and (c) a Google News query pre-filled with the market title — clearly labeled as a *search*, not a verified cause. |
| F6 | **Demo site has no public market webpage for direct deep links** | Irregularity | Demo markets live behind `demo.kalshi.co` (login required to trade); public `kalshi.com/markets/...` pages document the *production* contracts of the same series. **Mitigation:** row source links point to (1) the exact demo REST URL that produced the value (official machine-readable source) and (2) the official kalshi.com series page for the contract rules. |
| F7 | **Sub-cent/edge fields not exercised live** | Unverified at runtime | `settlement_bounds_type`, `collateral_return_type` values beyond defaults were not observed in live probes (no settled range market with partial payouts was sampled). These fields are displayed only when present, never inferred. |
| F8 | **"Highest dollar amount" ranking metric is a defined approximation** | Methodology (documented) | No official "dollar amount per event" metric exists. Raw contract counts are displayed alongside so nothing is hidden. |
| F9 | **KXPRES28 probe failed twice (fetch tool error, not API-verified)** | Unverified | A direct probe of `GET /series/KXPRES28` errored at the fetch-tool level twice; the 2028 presidential series is therefore *not* claimed as verified for demo. | F10 | **Client polling can lag the exchange by several seconds** | Documented limitation | Official docs state market-data responses are **cached for a short time** and can lag the exchange by several seconds ([Get Markets](https://docs.kalshi.com/api-reference/market/get-markets.md), [Candlesticks](https://docs.kalshi.com/api-reference/market/get-market-candlesticks.md)). The site displays a "last updated" timestamp per panel and labels all prices with their fetch time. |
| F11 | **Developer Agreement §3.1 / §3.5 / §6.4 vs this repo's pipeline** | **Needs the owner's decision** (raised 2026-11-21, `9b6ffae0`) | The [Kalshi Developer Agreement v1.1](https://assets.kalshi.com/Kalshi-Developer-Agreement.pdf) limits API use to "facilitating a members own trading on the Exchange" (§3) and prohibits "Collecting, caching, aggregating, or storing data or content accessed via the API except for purposes of facilitating your own trading on Kalshi" and sharing it "with third parties in any manner without prior written authorization from Kalshi" (§3.1). This repo stores API snapshots in git and publishes them on a public Pages site, and it also probes `GET /exchange/status` + records per-request timings, which sits next to §3.5 ("monitoring the availability, performance, or functionality of any of Kalshi's services or for any other benchmarking or competitive purposes"). §6.4 requires prior written approval for "public statements … relating to Kalshi, the Kalshi Marks, Kalshi Services, Kalshi API, or this Agreement". The agreement as read contains **no demo-environment carve-out**. No legal conclusion is drawn here; options are: keep the site but stop committing raw snapshots publicly, make the Pages site private, or request written authorization. Positive finding in the same clause set: §4.3 *requires* "Retry with exponential backoff", "Retry a bounded number of times" and monitoring "with any dashboards and alerting required" — which is what the collector does after PR #80. |
| F12 | **`previous_price_dollars` was read as "the previous trade price"** | **Verified defect → fix requested** (2026-11-21, `9b6ffae0`) | The official schema defines it as "Price for the last traded YES contract on this market **a day ago** in dollars" ([Get Events — Market schema](https://docs.kalshi.com/api-reference/events/get-events.md)). `assets/app.js` `checkAlert()` and `executive-summary.html` describe the alert fallback as catching a swing "inside one poll window" using "the exchange's own `previous_price_dollars`" — that is a 24-hour comparison, not a sudden-move detector. Both files are claimed by other sessions, so change request **R1** (exact one-line relabel + comment fix, plus an optional guard) is logged in `COORDINATION.md`; nothing was edited here. Audit: [`../reports/VERIFICATION_9b6ffae0.md`](../reports/VERIFICATION_9b6ffae0.md) row 9b-J. |
| F13 | **Historical partition makes the Resolved archive and the tape-based charts shrink over time** | Documented behaviour; improvement requested | `GET /markets` / `GET /markets/{ticker}` drop settled markets older than `market_settled_ts`, and `GET /markets/trades` drops trades older than `trades_created_ts` ([Historical Data](https://docs.kalshi.com/getting_started/historical_data.md)).
