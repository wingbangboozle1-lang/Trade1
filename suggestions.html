Quick wins — static page, no new infrastructure

#SuggestionWhy it matters to a traderOfficial capability that makes it possibleEffort
1Batch the order book for the whole watchlist. Replace "selected market only" depth with one call covering up to 100 markets, and rank markets by resting size at ±1–3¢ of the touch. Shows how many contracts are available at a given price for every market at once, which is what actually tells you whether a $0.10 move is tradeable; it also turns "liquidity" from a derived number into an observed one. GET /markets/orderbooks?tickers=… — up to 100 tickers per request; returns yes bids and no bids only, levels as [price, quantity] sorted ascending, best bid last; unknown tickers come back as empty arrays (documented). small
2Rank by measured traded dollars, not by an estimate. Aggregate the tape (count_fp × yes_price_dollars) per market over a rolling window and use that for the "highest dollar amount" ordering; use taker_outcome_side to show which side was aggressive into the move. The site currently labels its dollar ranking as an estimate (volume_fp × last_price_dollars) because no per-market dollar field is published. The trade tape does contain the size and price of every execution, so the ranking can become measured, and "who hit whom" becomes visible next to each alert. GET /markets/trades — filter by ticker, min_ts/max_ts (seconds; milliseconds are rejected 400), limit ≤ 1000 with cursor pagination; block trades flagged by is_block_trade. small
3Desktop + sound alerts for the model chat (Notification API), with a per-topic mute and a "only ≥ $0.15" sensitivity slider. A chat you must keep looking at is not an alerting system; you need to be pulled back to the terminal when a swing clears your threshold. Browser API only — no Kalshi dependency; polling cadence stays as documented (rate limits). small
4Keyboard + URL state. j/k to walk rows, Enter to select, 1–6 for the chart window, a to toggle alert sound; put the selected ticker in the URL hash so a view is shareable and survives refresh. Decision speed: pointing at a chart is slower than pressing a key while the tape moves. No API impact; the ticker format is the documented market ticker. small
5Show the valid price grid on the depth ladder. Mark each level against the market's price_ranges bands and print the tick size. Tells you instantly whether the next level you would hit is 1¢, 0.5¢ or 0.1¢ away — that difference is most of the edge on the 90¢+ end where the gas and golf series sit. Fixed-point representation — price_ranges is "the source of truth for valid prices", the label price_level_structure must not be keyed off. small
6Exchange-state banner. Poll GET /exchange/status with the quotes and show "trading active / paused / shard down" next to the price, instead of silently showing stale numbers. A flat line that is actually an exchange pause is the fastest way to lose money on a "swing" that is not real. Same response this repo already captures in data/exchange-status.json (exchange_active, trading_active, per-shard status), documented at Get Exchange Status. small
7Adaptive polling. Read X-RateLimit-* headers, back off exponentially on 429 (documented body {"error":{"code":"too_many_requests"}}), and widen the poll interval when the bucket is low instead of hammering. Keeps the dashboard alive for everyone during a busy news hour rather than turning it into a 429 wall. Rate Limits and Tiers — read/write buckets, header names, and the documented "no Retry-After, back off yourself" behaviour. medium
8Replayable alert history. Write the alert feed out as dated JSONL from the CI pipeline and let the dashboard scrub through a past session with the same chat + chart, including what the model chat would have shown. You cannot judge a screener on a live tape only; replay makes the ROI screen auditable and testable after the fact. Data already exists: this repo commits data/portfolio.json alerts; the same pattern extends to a daily file. medium
9Sparklines and a heat strip per topic card (24 h move, distance to 50¢, spread, time to close), with the card clicking through to the pre-filtered dashboard. Right now the five topics are separate pages; a trader wants "which of these 5 buckets is moving right now" in one glance, then to drop into that bucket. Fields already in use: last_price_dollars, previous_price_dollars, close_time per Get Markets. small
10Simplify: one decision bar. Move the alert chats above the fold, collapse the table columns to Market / Last / Δ / Spread / 24 h $ / Closes, and put depth, candles and settings behind a "detail" disclosure. The brief's own goal — help a trader decide on a contract event. Fewer columns means faster scanning. UI only. small

Needs a small server (real-time, not near-real-time)

#SuggestionWhyWhat the official docs require
11WebSocket bridge for the tickers. A tiny signing proxy subscribes to ticker / trade / market_lifecycle_v2 and fans the stream out to the page (or pushes alerts server-side). Removes the 12-second REST sampling and the exchange's own response cache from the alert path, and gives you determined/settled the moment they happen instead of on the next poll. Demo socket wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2 (demo environments). The handshake must carry KALSHI-ACCESS-KEY, KALSHI-ACCESS-SIGNATURE and KALSHI-ACCESS-TIMESTAMP over the message timestamp + "GET" + "/trade-api/ws/v2"; public market-data channels still run inside that authenticated session (Quick Start: WebSockets). A browser cannot set headers on a WebSocket — that is why this site polls REST, and it is why a bridge is needed (flagged item). Keep-alive note: Kalshi sends a Ping only after 10 s idle, so a missing Ping does not mean a dead connection.
12Server-side alert engine that evaluates the ≥ $0.10 rule on the WS stream and posts to a channel (or writes a push notification) so an alert exists even with no tab open. The current chats only fire while a browser tab is open; the CI ledger catches 30-minute swings but not the second-scale move that a trade needs. Same auth model as #11; nothing new in the API.
13Longer chart history: day candles plus the historical endpoint for markets past the cutoff, so the window picker can offer 7 days / 30 days. Election and golf series move over days; a 24 h window is the current ceiling. Get Market Candlesticks (period 1 / 60 / 1440 minutes) and Historical Data for markets settled before the cutoff.

Needs your demo API key (owner action, not a code gap)

#What is readyWhat is missingOfficial setup path
14The paper ledger already models fees, fills at official quotes and settles on official results — swapping quotes for your own demo account's balances and positions is a data-source change, and session 20e3ad14 built a guarded implementation of exactly that in scripts/demo_account/** (open draft PR #2: signing, read-only balance/positions, max 3 orders and $3.00 per run, dry-run by default). A demo API key ID and your own private key, stored as repository secrets by you. No agent can create or hold them, and this site never asks for them in the browser. Demo environment → create a demo account → API keys → authenticated requests.
15Maker-fee modelling so the lab can quote limit-order P&L instead of crossing every time. A decision on which fills you want simulated as resting orders; maker multiplier is per series (e.g. KXAAAGASM, the US gas price series, lists maker 1 / taker 1, so gas markets do carry a maker fee). Fee schedule PDF (maker: roundup(M × 0.0175 × C × P × (1−P))) and kalshi.com/fee-schedule for scheduled changes.

Suggested build order

  1. #1 batched order books and #2 measured traded dollars — both replace estimates with exchange-published facts, and both make the alert list actionable rather than just interesting.
  2. #10 simplification + #4 keyboard/hash state, so the page reads as one decision tool.
  3. #3 notifications and #6 exchange-state banner, for trust ("is this number current, and is the exchange open?").
  4. #11 the WS bridge, when you are ready to run one small stateless service.
  5. #14 real demo-account tracking, the moment you add a demo API key.

Nothing on this page has been built on assumption: where a capability is not documented as published by Kalshi, the row says so instead of inventing a number or a field. Gaps and contradictions stay on Flagged for Review.
