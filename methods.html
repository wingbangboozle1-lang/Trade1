2. Field units & semantics

  • Prices: fixed-point dollar strings ("0.4500") with up to 4 dp; quantities: _fp strings with 2 dp — per Fixed-Point Representation. This site displays them as $ and ¢ without inventing precision.
  • Order book: bids only (orderbook_fp.yes_dollars / no_dollars = [price_dollars, count_fp], ascending, best bid last). YES ask ≡ 1 − best NO bid (official reciprocal rule) — per Orderbook Responses.
  • Liquidity shown is computed bid-side notional (Σ price × contracts over both sides) — the demo responses observed do not include the legacy liquidity field; where absent we leave it blank elsewhere.
  • “Est. traded $” = contracts × last price. The API publishes contract volume but no per-market dollar-notional field in demo responses; this is our estimate, always labeled.
  • REST market responses are cached by the exchange for a short time — prices lag the tape by seconds — per Get Markets and Market Data Quick Start.

3. Alert rule (the two chats)

On every watchlist poll (~12 s) each market's sampled price (last trade, falling back to best YES bid when no trade) is compared with the previous sample in whole 1/10000-dollar units (so an exact $0.66 → $0.56 move, which binary float renders as 0.09999…, still fires). If the change is ≥ $0.10 in either direction, an alert is posted to the all-events chat. A 45-second per-market cooldown stops oscillation from spamming the chats. Only sampled deltas are used: we do not claim causality, and we do not infer moves that happened between polls (REST lag — flagged). Implemented in assets/app.js → checkAlert().

Model chat (high-ROI screen) — an alert is also posted when the score below clears the threshold (default 0.45):

score = 0.30·min(vol24h / 2000, 1)
      + 0.25·min(volume  / 10000, 1)
      + 0.20·max(0, 1 − spread/0.15)
      + 0.25·min(|Δ| / 0.25, 1)

Inputs are exchange-reported fields (contracts volume, quotes). The weights are engineering choices documented here — not verified predictive alpha (flagged). Implemented in assets/model.js → score().

Fee verification — the published table, reproduced exactly

Our fee function reproduces every row of the schedule’s “General Trading Fees Table” (21 prices × 1 contract and × 100 contracts). The check runs automatically in tests/root_engine.test.js on every push and pull request. It found and fixed a real bug: the naive float expression ceil(0.07·C·P·(1−P)·100) gave $1.76 for 100 contracts @ $0.50 (binary float renders 1.75 as 175.00000000000003), while the official table says $1.75 — the function now computes in integer arithmetic.

6. Chart windows & order book

  • Seconds (60 s, 5 m, 15 m): live session samples from REST polling (one point per poll ≈ 12 s).
  • Minutes/hours (1 h): exchange 1-minute candlesticks (trade-price close) merged with the live tail.
  • Hours (6 h, 24 h): exchange 60-minute candlesticks merged with the live tail.
  • Y axis: contract price in dollars, scaled to the range of the plotted prints (padded by 2¢ and clamped to the legal $0.00–$1.00 grid, so a market trading at 45–52¢ is not flattened into a straight line); the axis labels show the real bounds. X axis: time, with a window selector from 60 s to 24 h. Hovering the line draws a crosshair and reads back the nearest official print or candle close — timestamp, price and which of the two sources it came from; nothing is interpolated. Candlesticks are “a few seconds behind” per official docs, and demo markets trade sparsely, so hour+ windows can contain only a few candles. ≥ $0.10 alert markers are plotted as dots on the line; the latest jump in the window is linked below the chart (Kalshi market + news-search lead, causality never claimed).
  • Order book: YES bid/ask and NO bid/ask ladders show contracts available at each price (bids are exchange-published; asks are derived by the reciprocal rule). We request ?depth=10 (official parameter: the best 1–100 levels per side, counted from the best bid) and show the 6 best of each. Computed bid-side liquidity (Σ price × contracts) is labeled computed. Source: Get Market Orderbook.

7. Rate-limit care

Unauthenticated public requests have their own (undocumented) limits; the client backs off exponentially on HTTP 429, polls while the tab is visible only, batches tickers ≤200 per request, and pauses polling when hidden. See Rate Limits and Tiers.

8. The always-on CI ledger (portfolio.html) — how it differs from the browser lab

The same four strategies run twice an hour inside GitHub Actions (scripts/portfolio_engine.py, workflow portfolio.yml), and their ledger is committed to data/portfolio.json instead of localStorage, so the record survives a reload and every visitor sees the same numbers. Consequences a reader should know:

  • Sampling. A move is detected by comparing one priced cycle with the next (~30 min apart), not consecutive ~12 s polls. A fast round-trip that returns to its start is invisible to it; a slow drift is caught. Time-based exits are therefore expressed as a maximum holding time counted in cycles, so the results are a slower-clock test of the same rules and are not comparable trade-for-trade with the lab.
  • Quotes. Only GET /markets?tickers=… is called per cycle (plus nothing else); settlement is read from the same response (status, result, settlement_ts copied verbatim), per Get Markets. A tickers-only query returns every matching market in one response with an empty cursor — documented behaviour this engine depends on.
  • Units. Prices are held as integers in 1e-4 USD (the official 4-decimal price precision), sizes in 1e-2 contracts, cash in micro-dollars. The ≥ $0.10 test is therefore exact at the boundary (see §4 and Fixed-Point Representation).
  • Sizing. Whole contracts only, sized so that cost + entry fee fits $25.00, capped by remaining cash. Fractional contract sizes exist (0.01 granularity) but are only supported on markets that allow them, and the engine does not read that permission per market, so it never requests a fractional size.
  • Fees. Taker per the published schedule with the rounding described in Fee Rounding: model fee rounded up to 6 decimals, then the balance change floored to the $0.01 alignment for non-direct members with the remainder booked as the rounding fee. Settlement is free (“There is no settlement fee.”). Maker fees are not modeled — every simulated fill crosses the spread. The browser lab in the Fee verification subsection of §4 rounds the same model fee up to a whole cent instead, so an individual leg can differ by up to $0.0099 between the two engines (in the conservative direction) — see §9.
  • Fills. The ledger fills at the same quoted price as the lab (entry at the ask, exit at the bid) and applies no slippage and no queue model, so it inherits the optimism already flagged in Flagged (item 10).
  • Relationship to the demo-account console. demo-account/ (merged from PR #39) is a third layer, and the only one that can show account values: it reads GET /portfolio/balance and GET /portfolio/positions with the owner's demo key, and can place guarded demo orders. It stays inert while the secrets are absent. Comparability rule for readers: the lab and this ledger are both quote-driven simulations and may be compared directionally only (see §8 bullets above and E2, E4); demo-account figures are real (demo) fills and must never be compared to either simulation.
  • Bootstrap gap. The first cycle of a fresh state seeds prices from the committed snapshot, so the first comparison can span hours. Each alert carries gap_minutes (and a wide gap label above 90 minutes) so a stale-quote delta is never read as a fast move.

9. Fee application — precise statement (clarifies §4, “Sizing / Fees” bullet)

§4 above says the taker fee is “applied on paper entries and exits”. Precisely, in both engines: a fee is charged on a buy at the ask (entry) and on a sell at the bid (take-profit, stop-loss or max-hold exit). A position that ends at settlement — which is how most lab trades end — pays out $1.00 per winning contract with no fee, because the published schedule states there is no settlement fee. So “entries and exits” means “entries and sale exits”, not “every trade closes with a second fee”. Source: kalshi.com/docs/kalshi-fee-schedule.pdf (effective 2026-07-07), and the code paths assets/model.js → settle() and scripts/portfolio_engine.py → settle().

Two rounding details, stated so the two engines are never compared digit-for-digit: the lab's fee() rounds the model fee up to a whole cent (Math.ceil(cents − 1e-9)/100 on integer price/count inputs, so the binary-float artifact that made the naive form print $1.76 instead of $1.75 cannot happen), while the ledger implements the newer Fee Rounding rule (ceil_6dp trade fee plus a $0.01-aligned balance change with the remainder as a rounding fee). Both reproduce every row of the published “General Trading Fees Table” at cent display precision; they can differ by less than a cent on a single leg. Maker fees are excluded on both sides — and they are not zero for the gas series: the fee schedule lists KXAAAGASM with maker multiplier 1 and taker multiplier 1, and the demo API independently reports fee_type: "quadratic", fee_multiplier: 1 for that series (§4, “Per-series fee structure”), so a resting-order strategy would be mis-priced in both simulators.
